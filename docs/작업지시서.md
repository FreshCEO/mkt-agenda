# 본부의제 보드 Claude Code 이관 작업지시서

- 작성일: 2026-11-18
- 요청자: 담당 팀장 (이하 요청자)
- 대상: 본부의제 보드 v4.1 (채팅에서 만든 HTML 한 파일짜리 시연본)
- 목적: 시연본을 실제로 돌아가는 서비스로 옮긴다. 이번 범위는 세 가지다. 깃허브 배포, 웹에서 바로 저장, 예약 메일 자동 발송.
- 범위 밖: 화면 디자인과 문구 수정. 자동화가 끝난 뒤에 따로 한다. 이번 작업에서는 화면 모양과 동작을 바꾸지 않는다.

이 문서는 Claude Code가 처음 읽는 인수인계서다. 0장부터 차례로 읽고, 11장의 정보를 먼저 받은 뒤 2단계부터 시작한다. 1단계(예시 화면 배포)는 정보 없이도 바로 할 수 있다.

---

## 0. 한 줄 요약

본부의제 보드는 매주 본부미팅 안건을 모으는 화면이다. 금요일 10시까지 각 팀장이 안건을 적고, 12시까지 사업부별로 점검하고, 13시에 주인팀장이 최종 공지하고, 월요일 8시 전에 출력한다. 지금은 입력 내용이 각자 브라우저에만 저장되고 메일은 사람이 복사해 보낸다. 이것을 깃허브 화면, 구글 시트 저장, 정해진 시각 자동 메일로 바꾼다.

가장 먼저 확인할 것은 메일이다. 구글 계정에서 보낸 메일이 회사 메일함에 제때, 스팸으로 빠지지 않고 도착하는지 모른다. 그래서 저장 연동보다 메일 도착 시험을 먼저 한다.

넘겨받은 직후 아래 세 줄이 모두 통과하는지 먼저 확인한다 (2026-11-18 기준 통과 상태).

```
python build.py sample && python tests/smoke_sample.py && python tools/check_public.py
python build.py real && python tests/test_real.py        # 58/58, 명암비 미달 0건
```

필요한 도구: Python 3, playwright (pip), Chrome, git, Node.js와 clasp (Apps Script 배포용).

## 2. 지금 화면의 구조

### 2-1. 화면

단일 HTML 파일이다. `#app` 안을 `render()`가 통째로 다시 그린다. 클릭은 `data-act`, 값 변경은 `data-ch`, 입력은 `data-in` 속성으로 한곳에서 받는다 (`A` 객체가 동작 모음).

| 화면 | 함수 | 내용 |
|---|---|---|
| 1. 안건 기입 | `vIn`, `vInput` | 제출 현황판 18팀, 팀장 입력 (안건마다 제목 줄과 내용 한 칸) |
| 2. 사업부별 점검 | `vChk` | 확인 담당별 미제출 팀, 미제출 알람 메일, 의제 체크 목록, 사업부별 점검 완료 |
| 3. 최종 공지 | `vPub` | 공지 전 점검, 최종 공지 메일, 취합본 |
| 4. 출력과 본부미팅 | `vMtg` | 한 장 보기와 인쇄, 출력 완료 표시, 녹취 요약 |
| 히스토리 | `vHistory` | 주차별, 팀별 보기. 팀 칸 오른쪽에 본부미팅 피드백 |
| 설정 | `vSettings` | 팀, 사업부와 확인 담당, 시각, 메일 양식, 백업 |

### 2-2. 시점과 단계

시점은 6개다 (`STAGES`). 화면 단계 4개(`PH`)가 시점을 묶는다.

| 번호 | 시점 | 하는 일 | 메일 |
|---|---|---|---|
| 0 | 화 09:00 | 새 주차 열림 (지난 주를 히스토리로, 지난 주 내용을 입력 칸에 채움) | 없음 |
| 1 | 금 10:00 | 안건 기입 마감 | 미제출 알람 (`remind`) |
| 2 | 금 12:00 | 사업부별 점검 마감 | 없음 |
| 3 | 금 13:00 | 최종 공지 | 최종 공지 (`report`) |
| 4 | 월 08:00 | 출력 완료 | 없음 |
| 5 | 월 오전 | 본부미팅, 미팅 뒤 요약 | 없음 |

- 1, 2, 3번 시각은 설정에서 바꿀 수 있다 (`S.set.times`, `stAt`, `stT`).
- 시연용 "직접 넘기기"와 "실제 시계 따르기" 두 방식이 있다 (`S.set.clock`, `realStage`, `tick`, `beat`).
- 주차 이름 규칙: 미팅 월요일의 일(日)을 7로 나눠 올림한 값이 주차다 (`weekLabel`).

### 2-3. 상태

전체 상태는 `S` 객체 하나이고 `localStorage`의 `hq-agenda-test-v41` 키에 저장된다.

```
S.active   이번 주: label, meeting, stage, subs(팀별 제출 시각), none(팀별 없음 체크), items(안건),
           late(마감 후 제출), fin(사업부별 점검 완료), notes(미팅 요약), printed, fix, resv(메일 예약 표시)
S.weeks    지난 주들: label, meeting, teams, cells(팀별 분류별 글), status, fb(팀별 미팅 피드백)
S.edits    주차별 안건별 포함 여부와 사업부장 코멘트
S.ord      주차별 분류별 순서
S.teams    팀 이름, 담당 사업부장, 팀장 메일
S.set      시각, 주인팀장, 사업부와 확인 담당(org), 받는 사람, 메일 양식(rs, rb), 취합 링크, 선택 사항
S.sent     메일 발송, 예약 표시 이력        S.log   활동 기록
S.role     보는 사람(head, owner, lead)      S.ui    화면 상태 (서버에 저장하지 않는다)
```

### 2-4. 메일 만드는 코드

| 함수 | 하는 일 |
|---|---|
| `mailText(label)` | 최종 공지 본문. 기존 주인팀장 메일 양식 그대로: 번호 제목, ■ 소제목, - 내용, 줄 끝 (사업부장) |
| `mailHtml(body)` | 본문 글을 서식 있는 HTML로. 번호 제목과 ■ 줄, 중점과제 안건 줄은 굵게 |
| `fillTpl(tp, who)` | 미제출 알람 양식의 {주차}, {마감일}, {미제출수}, {미제출팀} 등을 채움. who는 확인 담당 범위 |
| `mailDraft(type)` | 받는 사람, 참조, 제목, 본문을 묶어 돌려줌 |

이 양식은 실제 메일과 대조해 맞춘 것이다. 서버로 옮길 때 글자 하나도 바꾸지 않는다.

## 3. 목표 구조

```
[깃허브 페이지]  화면 (예시 데이터만 들어 있는 껍데기)
      |  키를 넣으면 fetch (POST, JSON)
[Apps Script 웹앱]  읽기, 저장, 권한 확인, 메일 예약
      |                      |
[구글 시트] 데이터 보관     [시간 트리거] 5분마다 보낼 메일 확인 후 발송
```

- 기한이(팀 마감 캘린더)가 이미 같은 구조로 돌아가고 있다. 호출 방식, 키 처리, 버전 충돌 처리는 기한이의 `index.html`과 `Code.gs`를 먼저 읽고 같은 방식으로 맞춘다.
- 구글 시트는 누구와도 공유하지 않는다. 웹앱이 소유자 권한으로 대신 읽고 쓴다. 팀장들은 구글 계정이 없어도 된다.
- 실제 안건, 사람 이름, 메일 주소는 저장소에 올리지 않는다. 시트와 스크립트 속성에만 둔다.
- Claude Code는 요청자 PC에서 실행한다. 기한이 이관 때 클라우드 환경에서는 script.google.com 접속이 막혀 있었다.

## 4. 단계별 작업

가장 불확실한 것부터 한다. 각 단계는 완료 기준을 통과하고 요청자께 보고한 뒤 다음으로 넘어간다.

### 1단계. 깃허브 배포 (예시 화면)

1. 저장소를 만든다 (11장 1번). `dist/index.html`을 깃허브 페이지로 내보낸다. 내보내는 방법은 Actions로 `build.py sample` 결과를 올리는 방식을 권한다.
2. 커밋 전에 매번 `tools/check_public.py`를 돌린다. pre-commit 훅으로 걸어 둔다.
3. `tests/test_real.py`의 시나리오를 예시 데이터 기준으로 옮겨 `tests/test_sample.py`를 만든다. 실제 이름과 숫자가 들어간 판정 문장만 예시 값으로 바꾸면 된다. Actions에서 이 테스트가 통과해야 배포되게 한다.

완료 기준
- 페이지 주소가 열리고 4단계 화면이 보인다.
- `git ls-files`에 `data.real`, `index.real`, `test_real`이 없다.
- `check_public.py` 통과, 예시 테스트 통과.

### 2단계. 메일 도착 시험 (최소 서버)

저장 연동 전에, 구글에서 보낸 메일이 회사 메일함에 어떻게 도착하는지부터 확인한다.

1. 11장 2번 계정으로 구글 시트 1개와 Apps Script 프로젝트를 만든다. clasp로 `server/`와 연결한다.
2. `Code.gs`에 아래만 먼저 만든다.
   - `sendMail_(type, snapshot)`: `mailText`, `mailHtml`, `fillTpl`을 그대로 옮긴 함수로 제목과 본문을 만들고 `MailApp.sendEmail`로 보낸다 (htmlBody와 일반 본문 둘 다, 보내는 이름 "본부의제 보드").
   - `mailq` 시트와 `dispatch()`: 5분 간격 트리거. 보낼 시각이 지난 예약 건을 찾아 보내고 결과를 적는다.
   - 6장의 시험 모드 안전장치.
3. 시험용 내용은 `data.real.json`에서 뽑은 한 주치를 스크립트 속성이나 시트에 넣어 쓴다 (저장소에는 넣지 않는다).
4. 7장의 시험 T1, T2, T3을 하고 결과표를 보고한다.

완료 기준
- T1, T2, T3 결과표 (도착 여부, 도착 시각 차이, 스팸함 여부, 서식 유지 여부).
- 화면이 만든 본문과 서버가 만든 본문이 같은 데이터에서 글자 단위로 같다 (대조 테스트).

갈림길
- 도착하지 않거나 스팸함으로 가면 3단계로 가지 말고 멈춘다. 8장의 대안을 정리해 보고하고 결정을 받는다.

### 3단계. 웹에서 바로 저장

1. 5장의 API와 시트 구조를 만든다.
2. 화면에서 `localStorage` 저장을 서버 저장으로 바꾼다.
   - 열 때: 키가 있으면 서버에서 이번 주와 설정을 받아 그린다. 키가 없으면 예시 화면에 "키가 필요합니다" 안내만 보인다.
   - 팀장 입력: [저장] 버튼(임시 저장)과 [제출] 버튼. 누르면 서버에 바로 반영하고 "저장됨 15:02"처럼 보여 준다.
   - 저장 실패: 쓴 내용을 브라우저에 남겨 두고 다시 시도 버튼을 보여 준다. 쓴 글이 사라지면 안 된다.
   - 같은 팀을 두 곳에서 고친 경우: 버전이 다르면 덮어쓰지 않고 알린다 (기한이의 version 방식).
   - 제출 현황판은 1분마다 다시 받아 온다.
3. 시점은 서버 시계로 정한다. 화면의 "직접 넘기기"는 시연 주소(예: `?demo=1`)에서만 남긴다.
4. 화 09:00 주차 넘김은 서버 트리거가 한다 (`rollover`를 서버로 옮긴다). 미팅 요약이 히스토리로 들어가는 것도 이때다.
5. `data.real.json`의 11주치와 팀, 설정을 시트로 한 번 옮기는 스크립트를 만든다 (내 PC에서 관리 키로 실행).

완료 기준
- 브라우저 두 개(일반 창과 시크릿 창)에서 한쪽이 제출하면 다른 쪽 현황판에 1분 안에 보인다.
- 새로 고쳐도, 다른 PC에서 열어도 쓴 내용이 그대로다.
- 입력 키로는 설정 변경, 점검 완료, 메일 예약이 서버에서 거절된다.
- 키 없이 API를 부르면 아무 데이터도 나오지 않는다.
- 화면 시나리오 테스트가 서버 연결 상태에서 통과한다 (시험용 시트를 따로 둔다).

### 4단계. 예약 메일 본 구현

1. 금 10:00 미제출 알람, 금 13:00 최종 공지를 서버가 그 시각의 데이터로 만들어 보낸다. 시각은 설정의 값을 따른다.
2. 화면의 메일 상자를 서버 상태와 연결한다. "예약해 둠으로 표시" 버튼은 없애고 실제 상태를 보여 준다: 예약됨(보낼 시각), 보냄(보낸 시각), 건너뜀(사유), 실패(사유). 버튼은 [예약 취소], [나에게 시험 발송] 두 개.
3. 미제출 팀이 없으면 알람은 건너뛴다. 확인 담당별로 나눠 보낼지는 11장 6번 결정에 따른다.
4. 같은 메일이 두 번 나가지 않게 한다 (`LockService`, 주차와 종류로 중복 확인).

완료 기준
- 7장의 시험 T4 (금요일 실제 일정 리허설, 받는 사람은 요청자 한 명).
- 화면에서 예약 취소를 누르면 그 시각에 나가지 않는다.

### 5단계. 리허설과 전환

1. 한 주 동안 실제 일정대로 돌리되 메일은 시험 모드로 둔다.
2. 결과를 정리해 요청자께 보고한다. 실제 수신자로 바꾸는 것은 요청자이 직접 한다 (6장).

## 5. 서버 설계

### 5-1. 호출 형식

기한이와 같다. POST로 `{ op, key, who, args }`를 보내고 `{ ok, data | error }`를 받는다.

| op | 누가 | 하는 일 |
|---|---|---|
| `boot` | 입력 키 이상 | 설정, 팀, 이번 주 상태, 지금 시점, 내 권한 |
| `week` | 입력 키 이상 | 지난 주 한 주치 (히스토리) |
| `saveTeam` | 입력 키 이상 | 한 팀의 안건 임시 저장. `{ team, items, none, version }` |
| `submitTeam` / `unsubmit` | 입력 키 이상 | 제출, 제출 취소. 서버가 시각과 마감 후 여부를 기록 |
| `setEdit` | 관리 키 | 안건 포함 여부, 코멘트, 순서 |
| `fin` / `unfin` | 관리 키 | 사업부별 점검 완료, 취소 |
| `notes` | 관리 키 | 미팅 요약 추가, 수정, 삭제 |
| `printed` | 관리 키 | 출력 완료 표시 |
| `config` | 관리 키 | 시각, 주인팀장, 사업부와 확인 담당, 메일 양식, 팀 목록 |
| `mailq` | 관리 키 | 예약 목록 조회, 취소, 나에게 시험 발송 |
| `export` | 관리 키 | 전체 백업 JSON |

- 저장은 팀 단위로 한다. 전체 상태를 통째로 덮어쓰는 호출은 만들지 않는다 (18팀이 동시에 쓰면 서로 지운다).
- `who`에는 화면에서 고른 팀이나 역할을 넣어 기록에 남긴다.

### 5-2. 시트 구성 (안)

| 시트 | 열 | 비고 |
|---|---|---|
| `config` | key, json | 시각, 주인팀장, org, 양식, 받는 사람 |
| `teams` | name, head, mail, order | |
| `week` | label, meeting, fin(json), printed, fix(json) | 이번 주 1줄 + 지난 주들 |
| `team_week` | label, team, submittedAt, late, none(json), items(json), version, updatedAt, by | 이번 주 입력. 팀당 1줄 |
| `cells` | label, team, cat, text, status | 지난 주 보관본 |
| `edits` | label, itemId, inc, memo, order | |
| `notes` | label, id, team, text | 주차 넘김 때 `fb`로 보관 |
| `mailq` | id, label, type, dueAt, status, sentAt, to, subject, note | |
| `log` | ts, who, msg | |

- 긴 글은 팀 단위로 나눠 한 칸에 너무 많이 넣지 않는다 (칸당 글자 수 한도가 있다. 정확한 한도는 구글 문서에서 확인).
- 처음 여는 속도가 느리면(Apps Script는 첫 응답이 1~3초 걸릴 수 있다) 불러오는 동안 표시를 넣는다.

### 5-3. 키

- 키는 2개로 시작한다. 입력 키(팀장), 관리 키(주인팀장, 확인 담당, 사업부장).
- 주소 끝 `#k=키` 방식. 키 값은 스크립트 속성에만 둔다. 저장소, 문서, 커밋, PR, CLAUDE.md 어디에도 쓰지 않는다.
- 팀장 화면에서 다른 팀 누적 미제출, 메일 상자가 안 보이는 지금 동작은 서버 권한으로도 지킨다 (화면에서 숨기는 것만으로 끝내지 않는다).

## 6. 메일 안전장치 (반드시 지킬 것)

1. 시험 모드가 기본이다. 스크립트 속성 `MAIL_MODE`가 `live`가 아니면 모든 메일은 `TEST_TO` 한 곳으로만 간다.
2. 시험 모드 메일은 제목 앞에 `[시험]`을 붙이고, 본문 맨 위에 "원래 받는 사람"과 "원래 참조"를 적는다.
3. `MAIL_MODE`를 `live`로 바꾸는 일은 Claude Code가 하지 않는다. 요청자이 Apps Script 화면에서 직접 바꾼다.
4. 코드에 실제 메일 주소를 쓰지 않는다. 주소는 시트와 스크립트 속성에서만 읽는다.
5. 하루 발송 상한을 코드에 둔다 (기본 10통). 넘으면 보내지 않고 `mailq`에 실패로 남긴다.
6. 발송 전에 `MailApp.getRemainingDailyQuota()`를 확인한다.
7. 받는 사람이 비어 있거나 주소 형식이 아니면 보내지 않는다.

참고 한도 (구글 공식 문서 기준, 2026-11-18 확인)
- 개인 구글 계정은 하루 받는 사람 100명까지 보낼 수 있다.
- 트리거 실행 시간 합계는 하루 90분까지다. 5분 간격 확인은 하루 288회이고 한 번에 몇 초라 여유가 있다.
- 시각을 정하는 트리거(`nearMinute`)는 앞뒤 15분 오차가 있다. 그래서 정시 트리거를 쓰지 않고 5분 간격으로 "보낼 시각이 지난 건"을 찾는 방식을 쓴다. 간격은 1, 5, 10, 15, 30분 중에서만 고를 수 있다.

## 7. 메일 시험 절차

받는 사람은 전부 요청자 회사 메일 1곳(`TEST_TO`)이다.

| 시험 | 방법 | 확인할 것 |
|---|---|---|
| T1 즉시 발송 | 미제출 알람 1통, 최종 공지 1통을 바로 보낸다 | 도착 여부, 받은편지함인지 스팸함인지, 보낸 사람 표시, 굵은 글씨와 ■ 기호와 줄 맞춤, 휴대폰 화면 |
| T2 예약 발송 | 10분 뒤로 예약 3건을 건다 | 예약 시각과 실제 도착 시각 차이 (3건 모두 기록) |
| T3 예약 취소 | 10분 뒤 예약을 걸고 5분 뒤 취소한다 | 그 시각에 오지 않는지 |
| T4 금요일 리허설 | 실제 일정(금 10:00, 13:00)으로 건다 | 그 시각의 제출 현황이 본문에 들어갔는지, 미제출 0팀일 때 알람을 건너뛰는지 |

결과 보고 형식

```
[본부의제 보드] 메일 시험 결과 (날짜)
- T1: 알람 도착 O/X (위치), 공지 도착 O/X (위치), 서식 유지 O/X, 보낸 사람 표시: ...
- T2: 예약 14:10 -> 도착 14:12, 14:13, 14:11 (최대 3분)
- T3: 취소 후 미도착 확인 O/X
- 문제와 제안: ...
```

## 8. 메일이 구글에서 안 될 때의 대안

2단계에서 도착하지 않거나 스팸함으로 가면 아래를 차례로 검토해 보고한다. 결정은 요청자이 한다.

| 대안 | 방식 | 걸리는 점 |

| 회사 메일 예약 발송 | 요청자 PC의 브라우저에서 메일쓰기 화면에 붙여넣고 예약 | PC가 켜져 있어야 하고 사람이 확인해야 한다. 예약 시점의 내용으로 굳는다 |
| 회사 메신저 봇 | 메일 대신 메신저 알림 | IT에 앱 등록을 요청해야 한다 |
| 화이트리스트 요청 | 보내는 구글 주소를 회사 메일 관리자가 허용 | IT 협조 필요 |

## 9. 작업 원칙

1. 화면 모양과 문구는 바꾸지 않는다. 바꿔야 연결이 되는 곳(저장 버튼, 메일 상자 상태, 불러오는 중 표시)만 최소로 고친다.
2. main에 바로 올리지 않는다. 브랜치에서 작업하고, 테스트 결과와 화면 캡처를 붙여 PR로 올린 뒤 요청자 확인을 받는다.
3. 메일 양식(`mailText`, `mailHtml`, `fillTpl`)은 글자 하나도 바꾸지 않는다.
4. 실제 수신자에게 가는 메일은 이번 작업에서 한 통도 보내지 않는다.
5. 시트 데이터를 지우거나 통째로 바꾸기 전에는 `export`로 백업하고, 바꾸기 전과 후를 보고한다.
6. 모르는 것은 지어내지 않고 "확인 필요"로 남긴다. 사업부 구분, 사람 이름, 주소는 특히 그렇다.
7. 화면에 보이는 문구는 존댓말로, 쉽고 짧게 쓴다.
8. 예시 녹취록과 예시 피드백은 "화면 확인용 예시" 표시를 유지한다.
